# controller 控制器
- 监控当前状态
- 将当前状态转变为期望的状态

在机器人技术和自动化领域，控制回路（Control Loop）是一个非终止回路，用于调节系统状态。
这是一个控制环的例子：房间里的温度自动调节器。
当你设置了温度，告诉了温度自动调节器你的期望状态（Desired State）。 房间的实际温度是当前状态（Current State）。
通过对设备的开关控制，温度自动调节器让其当前状态接近期望状态。
在 Kubernetes 中，控制器通过监控集群 的公共状态，并致力于将当前状态转变为期望的状态。
● 上述是 k8s 官网给出的控制器的说法


解释: 如果我们部署 3台 nginx
如果使用pod 部署, 那么就需要  启动3个 pod
入如果 controller 就可以 声明 我要启动 3台nginx ,至于启动, 是k8s的事情, 反正就要启动3台ngixn
此时 k8s 会 根据 我们的声明, 启动3台nginx, 当有1台nginx 挂了, 此时 我们期望是启动3台nginx ,而此时 ,实际启动的是2台nginx
k8s会 自动的, 去在启动一台
就像是空调一样, 我们设定了温度27度, 我们就不用管了, 当室内温度,不是27度时, 空调会自动调节温度,保证和我们设置的温度相同


简单理解: controller 就是管理 pod的对象


# 常见控制器 controller

Deployment(控制器): 他是一个 controller , 他封装了 replicaSet 控制器, 所以说现在的 Deployment 其实是一个 复合的控制器
    以前 Deployment 控制器, 和  replicaSet 控制器,是分开的
    现在 Deployment 控制器 = Deployment + replicaSet

    Deployment的作用 : 管理多个副本, 确保 pod 按照预期的运行

DaemonSet(控制器): 每个节点 ,最多运行一个 Pod的副本场景
    解释: 就是每个节点运行一个 ,例如 日志, 网络,节点监控等
    选择 DaemonSet 来部署上述应用，主要因为它具备以下优势：

    保证全覆盖：能确保集群中每个符合条件的节点都运行着服务副本，不留死角。

    自动化管理：当集群新增节点时，DaemonSet 会自动在新节点上创建 Pod；当节点被移除时，也会自动清理对应的 Pod。

    简化配置：可以轻松访问节点的本地资源（如日志目录/var/log、设备文件等），这是这些节点级服务所必需的。

StatefulSet(控制器)
    能够保证Pod 的每个副本 在整个生命周期中 名称是不变的
    (我们直接部署pod 其实名称就是不变的,但是如果部署的是 controller, 默认的 Deployment 名称是动态的,而 statefulset是不变的 )
    为每个 Pod 提供稳定的网络标识（如 Pod 名称固定）和持久化存储
    StatefulSet 就是部署 有状态应用的, 但是如果 部署一个单节点 有状态的应用, 此时 Deployment和 StatefulSet没区别
    但是如果部署集群, 就必须使用 StatefulSet


Job(控制器)
    - 数据迁移
    - 数据库备份
    - 备份恢复
    - 镜像构建
